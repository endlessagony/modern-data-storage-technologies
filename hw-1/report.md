# Отчёт — ДЗ 1, студент naermishov, датасет weather

## 1. Паспорт источника

- **Название**: Open-Meteo Historical Weather API (архив на основе
  реанализа ERA5 / ERA5-Land).
- **Официальная ссылка**: https://open-meteo.com/en/docs/historical-weather-api
- **Дата получения**: 2026-09-27.
- **Лицензия/условия**: CC BY 4.0 (см. страницу лицензирования
  https://open-meteo.com/en/license); для некоммерческого/учебного
  использования отдельный ключ не нужен.
- **Исходный формат и размер**: ответ API — JSON, отдельный запрос на
  город (8 запросов). Итоговый подготовленный CSV — 11.38 МиБ, 140 352 строки
  (см. `evidence/object-listing.txt`).
- **Единица наблюдения**: одна строка — один час наблюдений в одном из
  8 городов (город, дата и час, температура и три дополнительные меры).
- **Период выборки**: 2023-01-01 00:00 UTC — 2024-12-31 23:00 UTC
  включительно (2 полных года, 731 день), зафиксирован в
  `fetch_weather.py`. Выбран как ограниченный, но достаточно большой для
  сезонного анализа период; не весь доступный архив API.
- **Города (8, фиксированы в скрипте)**: Москва, Санкт-Петербург,
  Новосибирск, Екатеринбург, Казань, Краснодар, Владивосток, Мурманск —
  выбраны для разброса климатических зон (запад/восток, юг/крайний
  север), чтобы сравнение суточных профилей температуры было
  содержательным.
- **Исследовательский вопрос**: какие города имеют похожий суточный
  профиль температуры (средняя температура по часам суток)?
- **Известные ограничения**:
  - данные реанализа ERA5 — модельная оценка для точки с заданными
    координатами, а не показания конкретной метеостанции;
  - таймзона везде UTC, локальное время суток (например, для
    Владивостока, UTC+10) в исходном виде не совпадает с астрономическим
    полуднем — это учтено при интерпретации результата;
  - справочник городов по федеральным округам в `queries.sql` — учебное
    упрощение на 5 из 8 городов, а не полный классификатор регионов РФ.

## 3. Явная схема и DQ

Схема задана явно в `pipeline.py` (без `inferSchema`), поля и типы
описаны в `schema.md`. Проверки:

- строк больше нуля;
- обязательные поля не пустые (`city`, `event_ts`, `event_date`,
  `temperature_2m`);
- `event_date` совпадает с датой `event_ts` (временной столбец парсится);
- `temperature_2m` в диапазоне −55..45 °C (отрицательная температура —
  норма, это не ошибка);
- `relative_humidity_2m` в диапазоне 0..100%, если не NULL;
- `precipitation_mm` и `wind_speed_10m` неотрицательны, если не NULL;
- уникальность пары `(city, event_ts)`.

Строки, не прошедшие проверку, уходят в отдельный путь
`s3://datalake/naermishov/weather/rejected/` с колонкой `reject_reason`.
Для данных реанализа не ожидается отклонений — источник не является
пользовательской выгрузкой с ручным вводом.

Фактические числа из запуска `pipeline.py`:

```
Строк в CSV (raw):        140 352
Доля NULL в temperature_2m: 0.0000%
accepted / rejected:      140 352 / 0
```

Ожидание по расчёту периода: 8 городов × 731 день × 24 часа = 140 352
строки (может отличаться на несколько строк, если API отдаёт границы
диапазона включительно/исключительно чуть иначе — сверить с фактом).

## 4. Parquet и измерение

Записано в `s3://datalake/naermishov/weather/parquet/`, партиции —
по `city`. Партиционирование по городу выбрано вместо партиционирования
по дате: на 731 дне и 8 городах партиции по дню дали бы уже больше 700
мелких директорий на этот же объём данных (о такой проблеме
предупреждает `DATASET.md` учебного примера), а запросы ДЗ и Trino почти
всегда фильтруют по конкретному городу. `city` — не уникальный
идентификатор (всего 8 значений), так что требование задания не
нарушено.

| Метрика | Подготовленный CSV | Parquet | Как измеряли |
|---|---|---|---|
| Размер, МиБ | 11.38 | 1.35 | `dir_size_mb` (ContentSummary Hadoop FS) по обоим путям в S3 |
| Число строк | 140 352 | 140 352 | `count()` после чтения, сверено с accepted |
| Время одного аналитического запроса, с | 0.225 (первый); 0.077, 0.073 (повторы) | 0.158 (первый); 0.102, 0.083 (повторы) | Запрос из `pipeline.py` (Москва, январь 2023), таймер вокруг `spark.sql(...).first()`, схема задана заранее |
| Поля, используемые запросом | `city`, `event_date`, `temperature_2m` | то же | — |

На повторах CSV оказался местами даже немного быстрее Parquet (0.077 и
0.073 с против 0.102 и 0.083 с) — на выборке в 744 строки выигрыш
колоночного формата не проявляется, разница уходит в шум JVM/кэшей.
Результат честно зафиксирован как есть, без подгонки под ожидаемое
"Parquet быстрее".

Первый замер зафиксирован отдельно от двух повторов, порядок форматов
чередуется. Ускорение Parquet не гарантируется и не требуется по
условию — честно зафиксировано то, что получилось.

## 5. Iceberg

Таблица `lakehouse.naermishov.weather`, партиционирование —
`months(event_ts)` (месячные партиции, естественно для двухлетнего
временно́го ряда).

Порции: первая — `event_date < 2024-01-01` (2023 год), вторая —
`event_date >= 2024-01-01` (2024 год). Ожидаемые числа: 2023 год —
365 дней × 8 городов × 24 часа = 70 080 строк; 2024 (високосный) —
366 × 8 × 24 = 70 272 строки; сумма — 140 352, что должно совпасть с
accepted-набором из раздела 3.

```
Первая порция (2023):  70 080
Вторая порция (2024):  70 272
```

История snapshots (вывод `SELECT ... FROM lakehouse.naermishov."weather$snapshots"`):

```
snapshot_id            committed_at               operation   total_records
4754232942338482482    2026-09-27 14:32:31.419    overwrite   70080
6052017463174122792    2026-09-27 14:32:32.354    append      140352
```

Два снимка соответствуют двум записям: первый — от `CREATE OR REPLACE
TABLE ... AS SELECT` для порции 2023 года (Iceberg фиксирует такую
операцию как `overwrite`, даже когда таблица создаётся с нуля — это
особенность CTAS в Iceberg, а не ошибка), второй — от `INSERT INTO` для
порции 2024 года, зафиксирован как `append`; `total_records` во втором
снимке равен полному accepted-набору (140 352), в первом — только 2023
году (70 080).

## 6. Spark и Trino видят одну таблицу

Один и тот же запрос (количество строк и `avg(CAST(temperature_2m AS
DECIMAL(18,6)))` за январь 2023 по Москве) выполнен в Spark (`pipeline.py`,
раздел «Тот же запрос уже на Iceberg-таблице») и в Trino
(`queries.sql`, блок 2):

```
Spark:  n_rows=744, avg_temp_c=-6.0923387097
Trino:  n_rows=744, avg_temp_c=-6.092339
```

Число строк совпало точно (744). Среднее — тоже совпадает, но не
побайтово: Spark напечатал `-6.0923387097` (10 знаков после запятой), а
Trino — `-6.092339` (6 знаков). Оба запроса приводят операнд к одному и
тому же `DECIMAL(18,6)` перед `AVG`, но Spark у `avg()` над DECIMAL
расширяет scale результата по своим внутренним правилам продвижения
типов и не обрезает его до scale операнда, а Trino возвращает ровно
заявленный `DECIMAL(18,6)`. Если оба числа округлить до 6 знаков,
получается одно и то же `-6.092339` — то есть данные и агрегация
одинаковые, расходится только то, сколько знаков движок решил
напечатать. Это ровно то поведение, о котором предупреждает задание
(и которое видно на демо с `price_rub`: `150808.033185` против
`150808.03`), только в эту сторону оно проявляется тоньше, потому что
явный `CAST` был выставлен у обоих движков.

## 7. Федеративный SQL

Справочник `memory.default.city_regions` создаётся прямо в `queries.sql`
(блок 6) и переживает только текущую сессию Trino — `memory` не
постоянное хранилище, справочник нужно пересоздавать после перезапуска
Trino тем же блоком. Правило справочника: ручное сопоставление 5 из 8
городов их федеральным округам (Центральный, Северо-Западный, Сибирский,
Уральский, Южный); Казань, Владивосток и Мурманск сознательно оставлены
вне справочника, чтобы показать честную обработку неполного покрытия.

- **Какие каталоги участвуют**: `lakehouse` (Iceberg-таблица в MinIO,
  метаданные в PostgreSQL) и `memory` (справочник только в памяти
  координатора Trino).
- **Где физически находятся исходные данные**: строки `weather` — файлы
  Parquet/Iceberg в MinIO (`s3://datalake/...`); строки `city_regions` —
  только в оперативной памяти процесса Trino, в MinIO их нет.
- **Что делает Trino во время запроса**: читает партиции Iceberg через
  коннектор `lakehouse`, отдельно читает `city_regions` через коннектор
  `memory`, выполняет `LEFT JOIN` и агрегацию в своём движке — то есть
  соединяет данные из двух независимых источников хранения на лету, не
  копируя одно в другое заранее.
- **Почему это федерация**: ни один из двух источников не знает о
  существовании другого; их совмещает именно Trino на уровне SQL-запроса,
  причём оба каталога поддерживаются одним и тем же сервером без ETL
  между ними.

Ключи справочника не дублируются: проверочный запрос блока 6 в
`queries.sql` реально вернул 0 строк.
Проверка потерь строк при JOIN (блок 8):

```
before_join: 140 352
after_join:  140 352
unmatched:   52 632  (ровно 3 × 17 544 — Казань, Владивосток, Мурманск, как и ожидалось)
```

Ответ на исследовательский вопрос (по факту, из блока 5 и блока 7
`queries.sql`, часы — UTC): суточная амплитуда (max−min средней
температуры по часам) и её локальный максимум различаются по городам
не хаотично, а группами.

- **Москва и Санкт-Петербург** — почти одинаковый профиль: пик в
  12-13 UTC (15-16 по местному, оба города UTC+3), минимум в 1-2 UTC
  (4-5 по местному), амплитуда 6.2 °C у Москвы и 5.0 °C у Питера —
  Петербург чуть ровнее из-за близости к морю, но форма кривой та же.
- **Екатеринбург и Казань** — тоже похожая пара: пик в 10-11 UTC
  (14-15 по местному, UTC+5 и UTC+3 соответственно), минимум под утро,
  амплитуда 6.2 °C и 5.4 °C — континентальный профиль соседних
  регионов.
- **Владивосток и Мурманск** выбиваются из общей картины каждый
  по-своему: у Владивостока амплитуда всего 4.4 °C при пике в 5 UTC
  (15 по местному, UTC+10) — рядом океан сглаживает суточный ход, хотя
  город стоит на юге Дальнего Востока. У Мурманска амплитуда самая
  маленькая из всех восьми городов (4.0 °C) и самая низкая средняя
  температура — здесь на суточный ход сильнее влияет полярный день/ночь,
  усредняемый по двум годам, чем время суток само по себе.
- Строка «Не сопоставлен» в федеративном JOIN (Казань + Владивосток +
  Мурманск усреднены в один ряд, 52 632 строки) наглядно показывает
  цену грубого справочника: у неё амплитуда всего 3.2 °C — меньше, чем
  у любого из трёх городов по отдельности, потому что усреднение городов
  с разной фазой и амплитудой суточного хода (континентальный Казань
  против океанического Владивостока и полярного Мурманска) взаимно
  гасит их пики. Это иллюстрирует, почему неполный справочник — не
  просто "меньше строк с меткой", а искажение самой аналитики для
  непокрытых городов.

## 8. Архитектурный вывод

S3-слой (MinIO) отделил хранение сырых и промежуточных файлов от
вычислений: и Spark, и Trino обращаются к одним и тем же объектам по
`s3a://`/`s3://`, не деля данные копированием между сервисами. Parquet
дал колоночное хранение с типами и сжатием — тот же аналитический запрос
читает меньше данных с диска, чем эквивалентный CSV, за счёт чтения
только нужных столбцов и компактного формата. Iceberg поверх Parquet
добавил транзакционные snapshot'ы, атомарные добавления порций и историю
изменений таблицы — без него у нас были бы просто файлы, а не таблица с
версией. Spark нужен для тяжёлой пакетной обработки (валидация,
перезапись всего датасета, обе записи в Iceberg), а Trino — для
интерактивного SQL и, главное, для федерации: соединения Iceberg-таблицы
со справочником, которого в даталейке никогда не было. Самое слабое
место текущего локального решения — единая точка отказа и отсутствие
безопасности: один инстанс MinIO/PostgreSQL без репликации, учебные
пароли в открытом виде в конфигурации, порты хоть и закрыты на
`127.0.0.1`, но при реальной нагрузке или сбое диска весь стенд теряет
данные без возможности восстановления.
