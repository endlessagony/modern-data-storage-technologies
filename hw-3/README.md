# ДЗ-3. Администрирование и оптимизация в PostgreSQL: витрина ударов StatsBomb

Домашнее задание 3 по курсу «Современные технологии хранения данных».

Берём витрину из ДЗ-2 (удары плей-офф ЧМ-2022 и Евро-2024, «команда × день»), смотрим, как быстро она считается
при разном физическом устройстве таблицы, поднимаем кластер Patroni с двумя узлами, делаем логическую копию и
проверяем восстановление. Результаты измерений, планы, проверки и объяснения собраны в [report.md](report.md).
Здесь описано, откуда данные, что считаем, как всё запустить с нуля и как остановить, не потеряв данные.

## 1. Связь с ДЗ-2

В ДЗ-2 витрина `mart.mart_team_day_shots` строилась dbt-моделями из «звезды» `dds.fact_shot`. Здесь остаётся та же
предметная область, тот же бизнес-вопрос и то же определение мер, но меняется предмет исследования: не логика
загрузки, а физическая организация таблицы фактов.

Что перенесено из ДЗ-2 без изменений:

- источник (StatsBomb Open Data) и коммит репозитория `4b73468fc5b0f1950f9f66fada70ad3a4f9327cb`;
- зерно факта: один удар, ключ `(source_system, event_id)`;
- зерно витрины: команда × день матча, ключ `(source_system, team_id, match_date)`;
- правила мер: серия пенальти (`period = 5`) в витрину не входит; «в створ» это исходы `Goal`, `Saved`,
  `Saved to Post`; голы с пенальти считаются отдельно; xG суммируется;
- 31 матч плей-оффов ЧМ-2022 и Евро-2024 (866 ударов) остаются **контрольным срезом**: по нему проверяется смысл
  результата, и его числа совпадают с результатами ДЗ-2 (например, финал ЧМ-2022: у Аргентины 20 ударов,
  10 в створ, 3 гола, 1 с пенальти, xG 2.7583).

Что отличается:

- витрина считается запросом прямо к таблице фактов, а не dbt-моделью с публикацией. Поэтому в результате нет тренера
  (SCD2-атрибут команды) и названий команд: на физическое устройство таблицы они не влияют, а в исходных данных
  название одной команды бывает записано по-разному (`Caen` и `Stade Malherbe Caen`), и для этого нужен отдельный справочник;
- вместо плей-оффов двух турниров берётся **весь открытый набор StatsBomb** по тому же коммиту: 3961 матч и
  101 227 ударов. Так у таблицы появляется несколько лет данных для секций и индексов, а смысл результата по-прежнему
  проверяется на контрольном срезе. Синтетических данных в этой работе нет.

## 2. Источник и данные

[StatsBomb Open Data](https://github.com/statsbomb/open-data), бесплатное некоммерческое использование со ссылкой на
источник. Файлы скачиваются не с ветки `master`, а по коммиту `4b73468f…`, поэтому повторное скачивание даёт те же байты.

| Файл | Что это |
|---|---|
| `data/shots.csv.gz` | все удары открытого набора: 101 227 строк, 4,4 МБ. Одна строка = событие `Shot` |
| `data/matches.csv` | все матчи набора: 3961 строка (счёт, дата, команды, турнир, стадия) |
| `data/control_shots.csv`, `data/control_matches.csv` | контрольный срез: 866 ударов и 31 матч из ДЗ-2 |
| `data/source_manifest.json` | коммит, sha256 списков матчей, число файлов событий и контрольная сумма всех sha256 файлов событий |
| `data/fetch_shots.py` | скачивает всё это с нуля (`python data/fetch_shots.py`, около 8 минут, интернет нужен только для него) |

Готовые файлы лежат в папке, поэтому для запуска интернет не нужен. Порядок строк в файлах фиксирован, gzip пишется без
времени в заголовке: повторный запуск `data/fetch_shots.py` даёт побайтно те же файлы (это проверено сравнением sha256 всех
пяти выходных файлов).

Из каждого события `Shot` берутся идентификатор события, матч, дата матча, команда, игрок, период, минута и секунда, тип
удара, исход, часть тела и `shot.statsbomb_xg`. Остальное (координаты, freeze-frame и т. д.) для этой работы не нужно.

## 3. Контракт результата

| | |
|---|---|
| Потребитель | аналитик футбольной команды или журналист, готовящий разбор турнира (как в ДЗ-2) |
| Бизнес-вопрос | сколько ударов, ударов в створ, голов и ожидаемых голов (xG) создала каждая команда в каждый игровой день выбранного периода; кто забивает больше, чем «положено» по xG |
| Гранулярность факта | один удар (событие `Shot`); серия пенальти хранится с флагом `is_shootout` |
| Гранулярность результата | команда × день матча |
| Ключ факта | `(source_system, event_id)`; `event_id` это UUID события в источнике |
| Ключ результата | `(source_system, team_id, match_date)` |
| Меры | `shots`, `shots_on_target`, `goals`, `penalty_goals` (штуки); `xg` (сумма вероятностей гола по ударам команды, безразмерная, «ожидаемые голы»); `goals_minus_xg = goals − xg` |
| Единицы | штуки для счётчиков; xG и `goals_minus_xg` безразмерны, точность до 10 знаков (`numeric(12,10)`), суммы точные |
| Время | `match_date` это календарная дата матча по местному времени места проведения. Поле `kick_off` источника без часового пояса и не всегда верно (см. ДЗ-2), поэтому не используется; пересчёта поясов нет. Отметок времени загрузки в этой схеме нет |
| Фильтры запросов | `source_system = 'statsbomb'`, `NOT is_shootout`, полуоткрытый интервал дат `[от; до)` |

Два запроса витрины, [sql/query_narrow.sql](sql/query_narrow.sql) и [sql/query_wide.sql](sql/query_wide.sql), отличаются только
интервалом: 10 дней группового этапа Евро-2024 `[2024-06-14; 2024-06-24)` и девять лет `[2016-01-01; 2025-01-01)`.
Число строк, диапазон дат и доли строк под фильтрами приведены в разделе 1 отчёта.

## 5. Запуск с нуля

Нужны Ubuntu 24.04 (или WSL2) и `sudo` для установки пакетов. Команды ниже запускаются из корня работы (папка, где лежит этот файл):

```bash
scripts/setup_env.sh      # PostgreSQL 16, etcd 3.5.17 и виртуальное окружение Python (Patroni, psycopg2, pillow)
scripts/run_all.sh        # весь сценарий с нуля, около двух минут; вывод каждого шага пишется в results/*_output.txt
```

`scripts/run_all.sh` по очереди выполняет то же, что можно запускать вручную:

```bash
scripts/start_pg.sh                      # одиночный PostgreSQL на порту 5440
scripts/load_data.sh                     # CSV -> stage -> dds.match, dds.fact_shot (исходная таблица)
scripts/build_variants.sh                # таблица с индексом, две секционированные таблицы, побочная таблица для порядка полей
scripts/versions.sh                      # версии и ресурсы
scripts/partitions_check.sh              # границы секций, края интервалов, какие секции остались в планах
python python/check_equal.py              # EXCEPT ALL: таблицы и результаты запросов против исходных
python python/independent_check.py        # контрольный срез: расчёт по CSV против SQL
python python/bench.py                    # прогрев и 9 измеряемых повторов двух запросов на всех вариантах
python python/write_cost.py               # цена индекса и секций на записи
scripts/random_page_cost_check.sh        # выбор Seq Scan или Index Scan для широкого запроса при разной стоимости случайного чтения
scripts/backup_restore.sh                # pg_dump -Fc, pg_restore в другую базу, проверки восстановленной базы
python python/mvcc_two_sessions.py        # опыт двух сессий и блокировка
scripts/cluster_up.sh                    # etcd и два узла Patroni (порты 5501 и 5502)
scripts/cluster_demo.sh                  # роли, маркеры, switchover, отказ записи в реплику, отставание
python python/make_screenshots.py         # скриншоты из сохранённых выводов
```

Подключиться к базам можно обычным `psql`:

```bash
source config/env.sh
psql -p 5440 -d shots                  # одиночный сервер; после scripts/backup_restore.sh есть и база shots_restored
psql -p 5501 -d shots                  # узел Patroni node1 (кто из узлов лидер, определяется командой patronictl -c ~/hw3-stand/cluster/node1.yml list)
```

Пароль суперпользователя на узлах Patroni `postgres`/`postgres` (`config/env.sh` уже выставляет `PGPASSWORD`). Это учебный стенд:
на одиночном сервере вход с локального адреса без пароля, ключей и TLS нет.

## 6. Остановка, повторный запуск, очистка

```bash
scripts/stop_all.sh       # останавливает узлы Patroni, etcd и одиночный сервер; данные остаются в ~/hw3-stand
scripts/start_pg.sh       # снова поднять одиночный сервер с теми же данными
scripts/cluster_up.sh     # снова поднять etcd и оба узла; кто станет лидером, решает Patroni по состоянию в etcd
scripts/clean_stand.sh    # полностью удалить данные стенда, чтобы повторить scripts/run_all.sh с нуля
```

Файлы работы (скрипты, CSV, отчёт, выводы) `scripts/stop_all.sh` и `scripts/clean_stand.sh` не трогают. Файл логической копии
(`~/hw3-stand/backup/shots.dump`, около 24 МБ) лежит вне папки с работой и в отчёт не включается.

## 8. Границы работы

- Стенд работает без Docker: PostgreSQL, etcd и Patroni запускаются обычными процессами (как вариант B в ДЗ-2).
  `docker-compose` для этой работы не делался и не проверялся.
- Два узла Patroni и один etcd на одной машине это учебная схема. Она не доказывает устойчивость к отказу машины,
  диска или сети, и у DCS нет кворума (см. отчёт, раздел 4).
- Автоматический failover не выполнялся: это необязательное расширение, в задании оно не оценивается.
- Скриншоты в папке нарисованы `python/make_screenshots.py` из сохранённых выводов прогона: на каждом настоящий вывод
  соответствующей проверки и подпись, что он подтверждает. Если нужны снимки живого терминала, те же команды из
  раздела 5 можно выполнить и снять экран.
