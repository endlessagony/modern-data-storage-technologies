# Отчёт по ДЗ-3. Администрирование и оптимизация в PostgreSQL

Работа основана на витрине из ДЗ-2 (удары плей-офф ЧМ-2022 и Евро-2024, «команда × день»). Как запустить всё с нуля,
описано в [README.md](README.md). Все числа ниже взяты из сохранённых выводов прогона (`results/*_output.txt`,
`results/bench_results.json`, `results/bench_plans.txt`); скрипты, которыми они получены, лежат в `scripts/` и `python/`.

Измерения сняты на одной машине: Ubuntu 24.04, 2 логических ядра Xeon 2.1 ГГц, 8 ГБ памяти. Это виртуальная машина,
поэтому у повторных запусков заметный разброс; я показываю все значения, а не только медианы, и не делаю выводов из
различий, которые меньше этого разброса.

## 0. Коротко

- **Узкий запрос** (10 дней, 1 007 подходящих строк из 101 227, 1,0%): составной B-tree индекс
  сокращает работу в разы. Читается 87 буферов вместо 1 535, серверное время падает с
  9.3 до 0.5 мс (медианы, в 18,5 раза). Секции без индекса дают меньший эффект
  (1.74 мс), секции с индексом почти совпадают с одним индексом (0.49 мс против 0.5 мс).
- **Широкий запрос** (71 552 подходящих строк, 70,7%): порядок величин не меняется ни у индекса, ни у секций.
  Последовательное чтение здесь правильный выбор. Секционированные варианты выглядят медленнее по `EXPLAIN ANALYZE`
  (46.3 и 48.7 мс против 41.4 мс), но это в основном накладные расходы замера узла `Append`: без замера узлов
  (38.4 и 34.1 мс против 32.8 мс) и по времени клиента разница в пределах разброса повторов.
- **Ответы совпадают** во всех вариантах: двустороннее `EXCEPT ALL` по таблицам и по результатам обоих запросов даёт 0 строк,
  независимый расчёт контрольного среза по CSV совпадает с SQL и с числами ДЗ-2.
- **Patroni**: два узла и etcd, роли определены по Patroni, REST API и SQL; маркер с лидера прочитан на реплике; после
  switchover роли поменялись, старый маркер на месте, новая запись доехала до новой реплики; запись в реплику отклонена.
- **Копия**: `pg_dump -Fc` восстановлен в отдельную базу командой `pg_restore` с кодом 0; структура, число строк, ключи,
  ограничения, контрольные строки и результаты запросов совпали с исходной базой.
- **Две сессии**: незавершённое изменение не видно другой сессии, после `COMMIT` видно; блокировка при изменении той же
  строки найдена через `pg_stat_activity`, `pg_blocking_pids` и `pg_locks`.

## 2. Что сравниваю и как измеряю

### Четыре варианта одной таблицы

Данные во всех вариантах одинаковы (проверено, раздел 3.5), различается только физическое устройство.

| Вариант | Таблица | Что в ней |
|---|---|---|
| исходная таблица | `dds.fact_shot` | куча, первичный ключ `(source_system, event_id)`, внешний ключ на `dds.match`, `CHECK` на период и xG |
| таблица с индексом | `dds.fact_shot_idx` | то же плюс B-tree `(source_system, match_date, team_id)` |
| секции | `dds.fact_shot_part` | `PARTITION BY RANGE (match_date)`, 13 секций, первичный ключ `(source_system, event_id, match_date)`, без других индексов |
| секции с индексом | `dds.fact_shot_part_idx` | то же плюс тот же составной индекс на родителе (по индексу в каждой секции) |
| побочный | `dds.fact_shot_idx_rev` | куча с индексом `(team_id, match_date, source_system)`; нужен только для проверки порядка полей |

DDL приведён в приложении A (файлы `sql/ddl_core.sql`, `sql/build_variants.sql`).

### Протокол измерения

1. Перед сравнением выполняется `ANALYZE` каждой таблицы.
2. Один прогревочный запуск каждого варианта в результат не входит.
3. Девять измеряемых повторов; внутри повтора варианты идут по очереди, чтобы медленный дрейф машины действовал на все одинаково.
4. В каждом повторе три раздельных измерения:
   - **серверное время**: `Execution Time` из `EXPLAIN (ANALYZE, BUFFERS)` (это основная колонка таблиц ниже), а также время
     планирования (`Planning Time`);
   - **то же серверное время без замера каждого узла**: `EXPLAIN (ANALYZE, TIMING OFF)`; нужно, потому что замер узлов сам
     стоит времени, и у планов с большим числом узлов (`Append` по 9 секциям) он заметнее;
   - **время клиента**: сам запрос с чтением всех строк ответа через `psycopg2`, от отправки до получения последней строки.
5. **cost** это оценка планировщика в условных единицах, а не время. В таблицах он вынесен в отдельную колонку и в выводах
   со временем не смешивается.
6. Это измерение после прогрева: вся таблица уже в `shared_buffers` (везде `read = 0`). Это не тест холодного диска.
7. Последовательное чтение не отключалось (`enable_seqscan = on`). Единственная настройка, влияющая на выбор планов, это
   `random_page_cost = 1.1` (SSD); её влияние показано отдельно в п. 3.3.

Загрузка данных и построение индекса измерены отдельно (п. 3.6).

- **С индексом** планировщик сам, без принуждения, выбрал `Index Scan` и `GroupAggregate` без сортировки: индекс отдаёт строки
  уже в порядке `(match_date, team_id)`. Работы по страницам больше: 5 876 буферов против 1 535
  (индекс вынуждает ходить в кучу за каждой строкой). Медиана серверного времени 33.0 мс против 41.4 мс, но диапазоны повторов
  перекрываются (31.4 – 36.5 против 37.9 – 54.7 мс), а по времени клиента разницы нет
  (45.6 против 42.9 мс). Осторожный вывод: индекс широкому запросу не мешает и, возможно, чуть помогает
  за счёт отсутствия сортировки, но порядка величин это не меняет.
- **Секции**: в плане 9 секций из 13 (отсечены `before_2015`, 2015, 2025 и 2026: вместе 29 367 строк, которые план не читает),
  буферов 1 093 против 1 535 (71,2%). Но по времени секции не выигрывают: 46.3 мс (с индексом 48.7 мс)
  против 41.4 мс по `EXPLAIN ANALYZE`; без замера узлов 38.4 и 34.1 против 32.8 мс; по времени клиента
  46.9 и 44.5 против 42.9 мс. Судя по планам: отсечённые данные и так отбрасывались дёшево (плоский `Seq Scan`
  отбрасывал 29 675 строк условием по дате), а подходящие 71 552 строк секционированный план читает и агрегирует так же, как и раньше. Добавились узел `Append`

  планировщик выбирает `Seq Scan` в каждой секции.
- Разница между временем по `EXPLAIN ANALYZE` и без замера узлов у секционированных планов заметно больше (46.3 и 38.4 мс),
  чем у плоского (41.4 и 32.8 мс): дополнительный узел `Append` протаскивает через себя все 71 552 строк, и его замер стоит времени. Поэтому по
  колонке «EXPLAIN ANALYZE» секции выглядят хуже, чем они есть, а по колонке без замера узлов и по времени клиента разница

сокращают чтение страниц лишь там, где условие отсекает большую часть данных. Объём работы, который они не могут убрать,
это чтение и агрегация 71 552 подходящих строк.

### 3.3 Индекс: порядок полей и его цена

**Порядок полей `(source_system, match_date, team_id)`** выбран по условиям запроса:

1. `source_system = 'statsbomb'` это условие на равенство. По контракту ДЗ-2 идентификаторы уникальны только внутри источника,
   поэтому любой запрос витрины обязан его содержать. Колонки с равенством идут первыми.
2. `match_date` это единственное условие-диапазон `[от; до)`. В B-tree по диапазону эффективно можно искать только по первой
   колонке, у которой нет равенства перед ней, поэтому диапазонная колонка идёт сразу после равенств.
3. `team_id` идёт последним: он есть в `GROUP BY` и не участвует в условиях. После него индекс отдаёт строки в порядке
   `(match_date, team_id)`, чего хватает `GroupAggregate` без сортировки (виден в планах).

В нынешних данных источник один, поэтому первая колонка не отсекает строк; она стоит первой потому, что так устроен контракт
запроса, а не ради выигрыша на этой выборке. Дубликаты ключа индекс хранит сжато (в `PostgreSQL` 13+ это дедупликация B-tree),
поэтому составной индекс занимает 1,0 МБ, около 8,3% размера таблицы.

**Проверка порядка полей.** На побочной таблице индекс построен в обратном порядке `(team_id, match_date, source_system)`.
Для узкого запроса планировщик всё равно берёт этот индекс, но диапазон по дате в нём не является границей просмотра: приходится
пройти по диапазону дат внутри каждой из 354 команд. Результат: 224 буферов против 87 у правильного порядка,
cost 1911 против 340, серверное время (медиана) 1.06 мс против 0.5 мс (диапазоны повторов 0.99 – 1.7 и 0.45 – 0.92 мс
частично перекрываются, поэтому опираюсь прежде всего на буферы и план). Для широкого запроса такой индекс планировщик не использует и читает таблицу целиком
(1 535 буферов). Порядок полей действительно имеет значение, и его определяют условия запроса.

**Почему у широкого запроса выигрыш от индекса небольшой, а выбор плана зависит от настройки.**
Индексный план выбран, потому что при `random_page_cost = 1.1` (SSD) случайное чтение стоит почти как последовательное, а индекс избавляет
от сортировки. При значении PostgreSQL по умолчанию (`random_page_cost = 4`) тот же запрос на той же таблице с индексом получает `Seq Scan`
(`results/random_page_cost_output.txt`):


Обе стратегии разумны для запроса, которому нужны 70,7% строк; планировщик не «ошибается», он сравнивает оценки стоимости. Из-за этого я

### 3.4 Секционирование

**Ключ**: `match_date`, диапазоны по календарным годам. Обоснование:

- оба запроса витрины фильтруют по `match_date`, поэтому условие по ключу секционирования есть в каждом запросе и планировщик
  может отсекать секции;
- время естественный ключ для данных, которые пополняются по датам матчей и со временем устаревают: старые секции можно отсоединять
  и архивировать целиком;
- по годам получается 13 секций разумного размера: от 913 до 20 751 строки в годовых, 9 535 в общей `before_2015`. Более мелкие

### 3.6 Что изменилось в объёме работы, что осталось прежним и какая цена

| | Узкий запрос | Широкий запрос |
|---|---|---|
| Строки, попавшие в ответ | 78, не изменились | 5 591, не изменились |

  отчётов по большей части таблицы выигрыша нет.

Замер загрузки и построения (`results/build_output.txt`, разовые значения, а не медианы): вставка в `dds.fact_shot_idx` при уже созданном
индексе 1249.2 мс, построение того же индекса с нуля 96.6 мс, вставка в секции 1206.7 мс и 1152.1 мс, построение индекса на секциях 151.2 мс.

**Switchover и failover.**

- *Switchover* это плановая, управляемая смена лидера при живом лидере. Patroni останавливает запись на старом лидере, дожидается,
  пока кандидат получит и применит весь журнал (включая запись остановки), повышает кандидата и переводит старого лидера в реплику.
  Потери подтверждённых транзакций при этом нет. Всё это видно выше: старый лидер на несколько секунд в состоянии `stopped`, затем
  становится репликой (`streaming`) и догоняет новую временную линию.
- *Автоматический failover* происходит, когда лидер пропал сам (процесс, машина, сеть): ключ лидера в etcd перестаёт обновляться,
  через `ttl` (30 с) истекает, реплики запускают выборы, и выигрывает тот, чей журнал не отстаёт больше, чем на
  `maximum_lag_on_failover`. При асинхронной репликации последние транзакции, которые лидер успел подтвердить клиенту, но не успел отправить реплике,
  теряются. Чтобы этого не было, включают `synchronous_mode`, ценой того, что запись останавливается при недоступности синхронной реплики. Вернувшийся бывший лидер
  приводится в соответствие через `pg_rewind` или переинициализируется. Автоматический failover я не выполнял (необязательное расширение).

**Отставание реплики.** Репликация асинхронная, поэтому реплика видит данные с задержкой; читать «только что записанное»
с реплики без ожидания нельзя. Поэтому скрипт не читает реплику сразу, а опрашивает её, пока маркер не появится. Отставание видно в
`pg_stat_replication` на лидере (`sent_lsn`, `replay_lsn`, `replay_lag`) и на реплике (`pg_last_wal_receive_lsn()`,
`pg_last_wal_replay_lsn()`, `pg_last_xact_replay_timestamp()`), а в Patroni колонкой `Lag` в `patronictl list`. В опыте оно равно 0 байт (задержка воспроизведения доли
секунды), потому что нагрузки почти нет, сеть это localhost, а обе базы на одной машине. Под нагрузкой, при медленном диске реплики или долгих запросах на реплике,
которые мешают применять журнал, отставание растёт. Данные `patronictl list` берутся из etcd и обновляются раз в `loop_wait` (10 с), то есть могут быть
на несколько секунд старше, чем `pg_stat_replication`; поэтому сценарий перед показом ролей ждёт, пока реплика перейдёт в `streaming`.

**Границы локального стенда.**

- Два узла и etcd работают на одной машине, на одном диске и одном питании. Это не доказывает устойчивость к отказу машины, диска или сети.
- В etcd один член, кворума нет: при его недоступности Patroni не сможет ни выбрать лидера, ни подтвердить существующего, и лидер
  через некоторое время перейдёт в режим только для чтения. В боевой схеме нужно минимум три члена DCS на разных машинах.
- Localhost скрывает сетевую задержку и потери пакетов, поэтому по опыту нельзя судить о реальном отставании реплики.
- Нет прокси или балансировщика перед узлами (HAProxy, VIP): клиенту приходится самому перечислять узлы и просить `read-write`.
  Нет ограждения (fencing) и сторожевого таймера (watchdog), пароли учебные.
- Failover не проверялся: показан только плановый switchover.

## 6. Опыт двух сессий

Таблица `demo.team_goals` из трёх строк; сессии `psycopg2` в отдельных соединениях (`python/mvcc_two_sessions.py`, `results/mvcc_output.txt`).
Опыт 1 идёт на уровне **READ COMMITTED** (по умолчанию в PostgreSQL), опыт 2 на **REPEATABLE READ**, опыт 3 снова на READ COMMITTED.

```
==============================================================================
ОПЫТ 1. READ COMMITTED (уровень по умолчанию): чтение, пока чужая транзакция не завершена
==============================================================================
  [сессия 1] show transaction_isolation
        transaction_isolation=read committed
  [сессия 2] show transaction_isolation
        transaction_isolation=read committed

--- сессия 1 меняет строку и НЕ завершает транзакцию
  [сессия 1] select txid_current() as my_txid
        my_txid=1209
  [сессия 1] update demo.team_goals set goals = 4 where team_id = 779
  [сессия 1] select team_name, goals, xmin, xmax from demo.team_goals where team_id = 779
        team_name=Argentina, goals=4, xmin=1209, xmax=0

--- сессия 2 читает ту же строку: видит старое значение
  [сессия 2] select team_name, goals, xmin, xmax from demo.team_goals where team_id = 779
        team_name=Argentina, goals=3, xmin=1208, xmax=1209

--- сессия 1 завершает транзакцию (COMMIT), сессия 2 повторяет чтение в своей транзакции
  [сессия 2] select team_name, goals, xmin, xmax from demo.team_goals where team_id = 779
        team_name=Argentina, goals=4, xmin=1209, xmax=0
  (READ COMMITTED: снимок берётся на каждый запрос, новое чтение видит зафиксированное значение; xmin новой версии = txid сессии 1)

==============================================================================
ОПЫТ 2. REPEATABLE READ: снимок фиксируется на всю транзакцию
==============================================================================
  [сессия 2] show transaction_isolation
        transaction_isolation=repeatable read
  [сессия 2] select team_name, goals from demo.team_goals where team_id = 779
        team_name=Argentina, goals=4

--- сессия 1 меняет строку и сразу фиксирует
  [сессия 1] update demo.team_goals set goals = 5 where team_id = 779

--- сессия 2 читает снова в той же транзакции: снимок прежний
  [сессия 2] select team_name, goals from demo.team_goals where team_id = 779
        team_name=Argentina, goals=4

--- после завершения транзакции сессии 2 новый снимок видит изменение
  [сессия 2] select team_name, goals from demo.team_goals where team_id = 779
        team_name=Argentina, goals=5

==============================================================================
ОПЫТ 3. Изменение той же строки второй сессией: блокировка и поиск ожидающего
==============================================================================

  (сессия 1: pid 827, держит блокировку строки и не завершена)

--- сессия 2 (pid 828) пытается изменить ту же строку и повисает
  через 1,5 с сессия 2 всё ещё ждёт: True

        pid=828, locktype=transactionid, mode=ShareLock, granted=False

        blocking_pid=827, blocking_state=idle in transaction, blocking_last_query=update demo.team_goals set goals = 6 where team_id = 779

--- сессия 1 завершает транзакцию, ожидание снимается, сессия 2 завершает свою

--- проверка: открытых транзакций не осталось
  [наблюдатель] select count(*) as idle_in_transaction from pg_stat_activity where datname = current_database() and state like 'idle in transaction%'
        idle_in_transaction=0
```

Как это объясняется через MVCC:

- `UPDATE` в PostgreSQL не переписывает строку на месте, а создаёт **новую версию** и помечает прежнюю: в `xmax` старой версии записывается
  номер транзакции, которая её удалила/изменила (`xmin` новой версии это её номер). В опыте 1 у старой версии `xmin = 1535`, `xmax = 1536`.
- Видимость версии определяет снимок сессии и статус транзакций-авторов. Пока транзакция 1536 не завершена, вторая сессия считает её изменения
  невидимыми: старая версия для неё ещё актуальна (значение 3), новой версии (значение 4) для неё нет. Читатель не ждёт писателя.
- После `COMMIT` транзакции 1536 новая версия становится видимой для новых снимков. На READ COMMITTED снимок берётся на каждый запрос,
  поэтому повторное чтение внутри той же транзакции уже видит 4. На REPEATABLE READ (опыт 2) снимок берётся при первом запросе и держится до конца
  транзакции: сессия 2 продолжает видеть 4, хотя сессия 1 зафиксировала 5, и видит 5 только после завершения своей транзакции.
- Опыт 3: вторая сессия пытается изменить строку, которую первая уже изменила и не зафиксировала. Она не может изменить «занятую» версию и встаёт в
  ожидание завершения транзакции первой (тип ожидания `Lock` / `transactionid`, запрошенная блокировка `ShareLock` на номер транзакции). Первая сессия
  находится в состоянии `idle in transaction`, то есть держит блокировку, ничего не выполняя, поэтому такие сессии опасны. После `COMMIT` первой сессия 2 выполняется и применяет свой
  `UPDATE` к свежей версии (получилось 6 + 100 = 106), потерянного обновления нет. При взаимном ожидании двух сессий срабатывает обнаружение взаимоблокировок, а `lock_timeout` ограничивает ожидание.
- Обе сессии в каждом опыте завершены (`COMMIT`), в конце проверено: открытых транзакций (`idle in transaction`) нет.

## 7. Объяснения своими словами

**WAL, восстановление после сбоя и репликация.** Write-Ahead Log это журнал изменений, который пишется раньше, чем изменённые страницы попадают в файлы данных.
Транзакция считается зафиксированной, когда её запись `COMMIT` сброшена в WAL на диск; страницы данных на диск могут попасть позже (при контрольной
точке). После сбоя сервер читает WAL с последней контрольной точки и заново применяет записи, поэтому потерянные из памяти изменения восстанавливаются, а
незавершённые транзакции остаются невидимыми: так обеспечиваются целостность и долговечность. Репликация опирается на тот же журнал: реплика
получает поток WAL от лидера и воспроизводит его, как при восстановлении, только непрерывно. Поэтому физическая реплика побайтно повторяет лидера, а отставание измеряется положением
в журнале (LSN). Слоты репликации не дают лидеру удалить WAL, который реплика ещё не получила.

**Почему репликация не заменяет резервную копию.** Реплика воспроизводит все изменения лидера, в том числе ошибочные: случайный `DROP TABLE`, `DELETE` без
условия, порча данных приложением дойдут до реплики за доли секунды. Копия же фиксирует состояние на момент времени, к которому можно вернуться. Реплика также не защищает от
логической порчи, ошибки в самом ПО, человеческой ошибки и от потери обоих узлов вместе (в этой работе оба узла лежат на одной машине и одном диске).

**Логическое восстановление и физическая копия с архивом WAL.** `pg_dump` делает *логическую* копию: набор команд/данных, из которых объекты создаются заново
(`CREATE TABLE`, `COPY`, `CREATE INDEX`), согласованный на момент начала выгрузки. Копию можно восстановить в другую версию PostgreSQL или на другую архитектуру, выбрать отдельные объекты, но
восстановление заново загружает данные и строит индексы (медленно на больших базах) и возвращает базу только к моменту выгрузки. *Физическая* копия (`pg_basebackup`) это копия файлов
кластера; вместе с непрерывным архивом WAL она позволяет восстановить кластер целиком на любой момент после копии (PITR), быстро для больших баз, но только на той же основной версии и архитектуре
и без выбора отдельных таблиц. Логическая копия проще и переносима; физическая с архивом WAL нужна, когда важны точка восстановления и скорость.

**Блокировка при изменении той же строки и как найти ожидающего.** Вторая сессия, изменяющая ту же строку, ждёт снятия блокировки строки: технически она
ждёт завершения транзакции первой (блокировка `ShareLock` на номер транзакции, в `pg_stat_activity` `wait_event_type = Lock`, `wait_event = transactionid`). Пока первая сессия не сделает `COMMIT`
или `ROLLBACK`, вторая простаивает. Найти ожидающего можно по `pg_stat_activity` (`state = active`, `wait_event_type = 'Lock'`), а блокирующего по функции `pg_blocking_pids(pid)`; непредоставленные
блокировки видны в `pg_locks` (`granted = false`). Ожидание ограничивается `lock_timeout`, а зависание из-за забытой транзакции можно предотвратить через `idle_in_transaction_session_timeout`;
`log_lock_waits` пишет в журнал ожидания дольше `deadlock_timeout`.

## 8. Оговорки

- **Шум измерений.** Машина виртуальная, повторы одного запроса различаются на 10–30% (диапазоны приведены в таблицах). Поэтому выводы делаются по
  планам и буферам (они детерминированы) и по различиям, которые больше разброса. Различия в 10–15% на широком запросе выводов не поддерживают.
- **Замер узлов.** Основная колонка «серверное время» это `EXPLAIN ANALYZE`, где каждый узел плана замеряется отдельно, и планы с большим числом узлов
  получают заметную добавку. Поэтому дополнительно приведено время без замера узлов и время клиента.
- **Размер данных.** 101 тыс. строк и 12,6 МБ таблицы целиком помещаются в `shared_buffers`, поэтому измерение показывает работу процессора и страниц в памяти,
  а не диска. На данных в сотни раз больше картина планов усилилась бы: параллельный `Seq Scan`, ощутимее выигрыш от отсечения секций, дороже случайные чтения. Проверять это на таких
  данных я не стал; вывод, что размер набора сам по себе не оценивается, относится и к этому отчёту.
- **Данные настоящие, синтетики нет.** Сравнение исходной таблицы, индекса и секций сделано на одном и том же наборе и одном и том же запросе; вклады разделены (п. 3.4).
- **Настройка планов.** Выбор плана для широкого запроса на таблице с индексом зависит от `random_page_cost` (п. 3.3).
- **Скриншоты** нарисованы `python/make_screenshots.py` из сохранённых выводов прогона, а не сняты с живого терминала. Каждый содержит настоящий вывод и подпись, что он подтверждает.

```sql
-- Одна строка факта = один удар (событие Shot), ключ (source_system, event_id), как в ДЗ-2.
-- Даты - календарная дата матча (match_date, без часового пояса), xG безразмерна: вероятность гола [0; 1].

create schema if not exists stage;
create schema if not exists dds;

drop table if exists stage.shots;
drop table if exists stage.matches;

create table stage.matches (

    away_team_name   text,

    away_score       int,

create table stage.shots (
    row_no        bigint generated always as identity,   -- порядок строк в файле
    source_system text,
    event_id      uuid,
    match_id      bigint,
    match_date    date,
    team_id       bigint,
    team_name     text,
    player_id     bigint,
    player_name   text,
    period        smallint,
    minute        smallint,
    second        smallint,
    shot_type     text,
    outcome       text,
    body_part     text,
    xg            numeric(12, 10)
);

drop table if exists dds.fact_shot;
drop table if exists dds.match;

create table dds.match (
    source_system    text   not null,
    match_id         bigint not null,
    match_date       date   not null,
    competition_id   int    not null,
    competition_name text   not null,
    season_id        int    not null,
    season_name      text   not null,
    stage_name       text   not null,
    home_team_id     bigint not null,
    home_team_name   text   not null,
    away_team_id     bigint not null,
    away_team_name   text   not null,
    home_score       int    not null,
    away_score       int    not null,
    primary key (source_system, match_id)

create table dds.fact_shot (
    match_date    date          not null,
    source_system text          not null,
    event_id      uuid          not null,
    match_id      bigint        not null,
    team_id       bigint        not null,
    player_id     bigint        not null,
    period        smallint      not null check (period between 1 and 5),
    minute        smallint      not null,
    second        smallint      not null,
    shot_type     text          not null,
    outcome       text          not null,
    is_shootout   boolean       not null,   -- серия пенальти (period = 5), в витрину не попадает
    is_penalty    boolean       not null,
    is_on_target  boolean       not null,   -- Goal, Saved, Saved to Post
    is_goal       boolean       not null,

    foreign key (source_system, match_id) references dds.match (source_system, match_id)
```

```sql
-- Четыре физических варианта одной и той же таблицы фактов (данные идентичны, различается только устройство):
--   dds.fact_shot          исходная таблица: куча + первичный ключ + внешний ключ (создана в ddl_core.sql)
--   dds.fact_shot_idx      то же + составной B-tree индекс под запросы витрины
--   dds.fact_shot_part     секционирование по match_date (RANGE, по годам), без дополнительных индексов
--   dds.fact_shot_part_idx секционирование + тот же составной индекс
-- Побочный вариант dds.fact_shot_idx_rev нужен только для проверки порядка полей в индексе.
\timing on

-- 1. Таблица с индексом. Порядок полей: source_system (равенство), match_date (диапазон), team_id (группировка).
create table dds.fact_shot_idx (like dds.fact_shot including defaults including constraints);
alter table dds.fact_shot_idx add primary key (source_system, event_id);
alter table dds.fact_shot_idx add foreign key (source_system, match_id) references dds.match (source_system, match_id);
create index fact_shot_idx_src_date_team on dds.fact_shot_idx (source_system, match_date, team_id);

\echo '-- вставка 101 тыс. строк в таблицу, где индекс уже есть (поддержка индекса при записи)'
insert into dds.fact_shot_idx select * from dds.fact_shot;

\echo '-- построение того же индекса с нуля на заполненной таблице'
drop index dds.fact_shot_idx_src_date_team;
create index fact_shot_idx_src_date_team on dds.fact_shot_idx (source_system, match_date, team_id);

-- 2. Секционированные таблицы. Границы секций: начало включается, конец исключается.
create table dds.fact_shot_part (like dds.fact_shot including defaults including constraints)
    partition by range (match_date);
create table dds.fact_shot_part_idx (like dds.fact_shot including defaults including constraints)
    partition by range (match_date);

do $$
declare
    parent text;
    year int;
begin
    foreach parent in array array['fact_shot_part', 'fact_shot_part_idx'] loop
        execute format('create table dds.%I partition of dds.%I for values from (%L) to (%L)',
                       parent || '_before_2015', parent, date '1900-01-01', date '2015-01-01');
        for year in 2015..2026 loop
            execute format('create table dds.%I partition of dds.%I for values from (%L) to (%L)',
                           parent || '_' || year, parent, make_date(year, 1, 1), make_date(year + 1, 1, 1));
        end loop;
    end loop;
end $$;

-- в ключ секционированной таблицы обязан входить ключ секционирования
alter table dds.fact_shot_part add primary key (source_system, event_id, match_date);
alter table dds.fact_shot_part add foreign key (source_system, match_id) references dds.match (source_system, match_id);
alter table dds.fact_shot_part_idx add primary key (source_system, event_id, match_date);
alter table dds.fact_shot_part_idx add foreign key (source_system, match_id) references dds.match (source_system, match_id);

insert into dds.fact_shot_part select * from dds.fact_shot;
insert into dds.fact_shot_part_idx select * from dds.fact_shot;

\echo '-- индекс на секционированной таблице (строится по каждой секции)'
create index fact_shot_part_idx_src_date_team on dds.fact_shot_part_idx (source_system, match_date, team_id);

-- 3. Проверка порядка полей: тот же набор колонок, но team_id стоит первым
create table dds.fact_shot_idx_rev (like dds.fact_shot including defaults including constraints);
insert into dds.fact_shot_idx_rev select * from dds.fact_shot;
create index fact_shot_idx_rev_team_date_src on dds.fact_shot_idx_rev (team_id, match_date, source_system);

vacuum (analyze) dds.fact_shot_idx;
vacuum (analyze) dds.fact_shot_part;
vacuum (analyze) dds.fact_shot_part_idx;
vacuum (analyze) dds.fact_shot_idx_rev;
```

## Приложение B. SQL запросов

Узкий запрос (`sql/query_narrow.sql`, для других вариантов меняется только имя таблицы):

```sql
-- Запрос 1 (узкий): витрина «команда x день» за 10 дней группового этапа Евро-2024, [2024-06-14; 2024-06-24).
-- Начало интервала входит, конец не входит. Удары серии пенальти не учитываются (как в ДЗ-2).
select f.source_system,
       f.team_id,
       f.match_date,
       count(*)                                          as shots,
       count(*) filter (where f.is_on_target)            as shots_on_target,
       count(*) filter (where f.is_goal)                 as goals,
       count(*) filter (where f.is_goal and f.is_penalty) as penalty_goals,
       sum(f.xg)                                         as xg,
       count(*) filter (where f.is_goal) - sum(f.xg)     as goals_minus_xg
from dds.fact_shot f
where f.source_system = 'statsbomb'
  and not f.is_shootout
  and f.match_date >= date '2024-06-14'
  and f.match_date <  date '2024-06-24'
group by f.source_system, f.team_id, f.match_date
order by f.match_date, f.team_id
```

## Приложение D. Конфигурация Patroni и запуск

`config/patroni_template.yml`:

```yaml
# Шаблон конфигурации узла Patroni. Значения в @...@ подставляет cluster_up.sh.
scope: hw3
namespace: /hw3/
name: @NAME@

restapi:
  listen: 127.0.0.1:@API_PORT@
  connect_address: 127.0.0.1:@API_PORT@

etcd3:
  host: 127.0.0.1:@ETCD_PORT@

bootstrap:
  dcs:
    ttl: 30
    loop_wait: 10
    retry_timeout: 10
    maximum_lag_on_failover: 1048576
    postgresql:
      use_pg_rewind: true
      use_slots: true
      parameters:
        wal_level: replica
        hot_standby: "on"
        max_wal_senders: 10
        max_replication_slots: 10
        wal_log_hints: "on"
  initdb:
    - encoding: UTF8
    - locale: C.UTF-8
    - data-checksums
  pg_hba:
    - local all all trust
    - host replication replicator 127.0.0.1/32 scram-sha-256
    - host all all 127.0.0.1/32 scram-sha-256

postgresql:
  listen: 127.0.0.1:@PG_PORT@
  connect_address: 127.0.0.1:@PG_PORT@
  data_dir: @DATA_DIR@
  bin_dir: @PG_BIN@
  pgpass: @PGPASS@
  parameters:
    unix_socket_directories: '@SOCKET_DIR@'
  authentication:
    superuser:
      username: postgres
      password: postgres
    replication:
      username: replicator
      password: replicator
    rewind:
      username: rewind_user
      password: rewind

tags:
  nofailover: false
  noloadbalance: false
  clonefrom: false
  nosync: false
```

Запуск узлов и etcd (`scripts/cluster_up.sh`): etcd стартует командой

```bash
etcd --name hw3 --data-dir <каталог> --listen-client-urls http://127.0.0.1:2379 --advertise-client-urls http://127.0.0.1:2379 \
     --listen-peer-urls http://127.0.0.1:2380 --initial-advertise-peer-urls http://127.0.0.1:2380 --initial-cluster hw3=http://127.0.0.1:2380
```

а каждый узел командой `patroni <каталог>/nodeN.yml`. Состояние: `patronictl -c <каталог>/node1.yml list`.
